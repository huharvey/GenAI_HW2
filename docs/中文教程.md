# 中文教程：从三个 Agent 到带审阅回路的多智能体系统

## 1. 先理解案例在做什么

案例的输入是一个技术主题，输出是一份带引用的中文小报告。多个 Agent 不共享同一个人格，而是分别承担规划、检索、写作和审阅任务。

基础版使用固定顺序，方便第一次运行时观察每一步：

1. `PlannerAgent` 把主题拆成检索问题。
2. `SearchAgent` 调用 `search_literature`，返回课程资料库和 Crossref 的来源。
3. `WriterAgent` 使用证据编号 `[S1]`、`[S2]` 生成报告。

提高版增加 `ReviewerAgent`：

1. 检查报告是否使用了真实的 `[S#]` 编号。
2. 找出没有证据支持的事实、重复和过度外推。
3. 如果需要修改，路由函数把任务交回 `WriterAgent`。
4. 最多修订一次，之后停止并保留审阅结果。

## 2. 为什么需要 Harness

如果只写四个 Prompt，系统很快会遇到三个问题：谁先发言、什么时候停止、怎样验证结果。代码中的 AutoGen Team 和运行函数正好承担这些 Harness 工作：

- 保存共享消息上下文
- 触发工具调用并记录工具结果
- 根据来源和状态选择下一位 Agent
- 通过 `REVIEW_APPROVED` 或最大轮数终止
- 将消息轨迹和证据注册表写入文件

因此学生可以把“模型能力”和“运行机制”分开观察。

## 3. 先运行基础版

```powershell
python basic.py --topic "multi-agent coordination for LLM systems"
```

打开最新的 `outputs/basic_*/trace.jsonl`，重点观察：

- PlannerAgent 是否真的提出了可检索的问题
- SearchAgent 是否调用了工具
- WriterAgent 是否使用了 `[S#]` 引用
- 终止词 `BASIC_REPORT_DONE` 是否让 Team 停止

## 4. 再运行提高版

```powershell
python advanced.py --topic "LLM-based agents for PLC code generation"
```

打开同一目录下的 `report.md` 和 `review.md`。如果报告第一次不合格，可以看到：

```text
WriterAgent → ReviewerAgent → WriterAgent → ReviewerAgent
```

这就是一个最小的“生成—检查—修订”闭环。代码没有把所有决策交给模型，而是用一个很短的 `choose_next` 函数限制协作范围。

## 5. 推荐学生修改的位置

### 修改 Agent 角色

可以把 `ReviewerAgent` 改成：

- 事实核查 Agent
- 反方 Agent
- 工程可行性 Agent
- 引用格式 Agent

保持每个角色只有一个主要职责，便于比较修改前后的效果。

### 修改工具

可以在 `research_tools.py` 中增加：

- 查询指定论文的元数据
- 计算表格中的比例
- 读取课程提供的 CSV
- 检查报告是否包含指定章节

工具应该返回可核查的结果，避免只返回“看起来合理”的自然语言。

### 修改评价指标

建议至少记录：

- 报告是否引用了真实来源
- 是否完成所有要求的章节
- Agent 轮数
- 是否发生修订
- 运行时间和 API 成本

还可以把多智能体结果和一个单 Agent baseline 进行比较。不是 Agent 越多越好，只有在分工带来可观察收益时才值得增加角色。

## 6. 实验安全边界

本案例只生成调研报告，不让 Agent 直接执行外部控制命令。即使今后加入 MCP 工具，也应先使用只读接口，并保留人工确认、超时和失败处理。
